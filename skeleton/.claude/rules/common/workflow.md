# Workflow — plan → work → review → ship

Загружается всегда (нет `paths`). Универсально для любого стека.

## Порядок инструментов — разведка → grill → plan → work

Инструмент привязан к фазе задачи, не к настроению. Валидация порядка (clarify-before-plan):
spec-kit `specify→clarify→plan→implement`, mattpocock grilling = pre-planning gate.

0. Разведка (сам) — grep/glob/read, макеты, доки под бюджет; факты собираю сам, не спрашиваю
   (`context-hygiene.md`).
1. grilling — ДО плана. Допрос по развилкам, по одному вопросу, к каждому рекомендация;
   стоп до «понимание достигнуто». Снимает design-выборы, чтобы план не зашил их молча.
   Механика — скил `core:grilling` (плагин `md-front-skills`), здесь не дублировать.
2. /plan — после grilling, с закрытыми решениями. Открытая развилка = план невалиден
   (`plan/SKILL.md`).
3. work → verify → review → ship (см. буллеты ниже).

`/compact` — ортогонально фазам, по границе окна, не по «этапу N»:

- проактивно на границе фазы и после тяжёлой MCP-фазы (макеты, браузер, большие дампы) —
  выжимку фактов в файл ДО compact;
- НЕ посреди задачи, когда ещё нужны ранние решения (офиц. дока Anthropic) — файл-выжимка страхует.

- **Plan first для нетривиального.** Многошаговая задача → план до кода. Однострочный
  diff — без церемоний. План обязан содержать секции из `/plan` (допущения/развилки,
  внешние контракты, teardown) плюс МОДЕЛЬ ДАННЫХ, если фича трогает структуры: неверно понятая
  модель уводит план, код и тесты в одну сторону, они согласуются между собой и остаются неверны
  вместе — единственный класс, который зелёный прогон не ловит по определению.
  Пустая обязательная секция → из планирования не выходим.
- **Spec как контракт.** Для сложного — явные критерии готовности (что должно работать)
  до реализации. Для примитива — типы + тест = спек.
- **Новый срез / boundary-фича → DoR-гейт ДО спеки и кода.** Входы (контракт бэка, форма данных,
  макет, копирайт) запрашиваются у владельца — они часто уже на руках. Пустой пункт гейта → срез
  не берём. Минимальный состав гейта: контракт границы, форма данных, макет или текст,
  критерий приёмки. Каждый либо получен, либо вслух назван отсутствующим — молчание за
  «получено» не считается. Чеклист входов и процедура — `.claude/docs/dor-gate.md`.
- **Объёмный док — агенту `scribe`. Порог: >60 строк или >6KB.** Считать в строках и
  килобайтах, не «на глаз в токенах»: неизмеримый порог не применяется. Правки существующего
  дока — точечными Edit; растущий док и лог — **append** через `scripts/log-append.sh`
  (его ставит bootstrap), не перезапись. Файл >40KB — не `Edit`, а Bash in-place: тул дифает
  файл целиком и висит минутами. Это НЕ только дисциплина: `guards/block-large-edit.sh`
  блокирует `Edit` от `LARGE_EDIT_KB` (по умолчанию 40) и предупреждает о крупном `Write`.
  Порог инстанса смотри в его `.harness.conf` — он мог быть поднят под самый большой файл.
- **Делегировать по умолчанию, делать самому — по причине.** Агенту уходит: механика по репо
  (`scout`), работа независимая от текущих правок (фон), задача, которой нужно чистое окно
  (ревью, ресёрч). В главной сессии остаётся то, что опирается на накопленный контекст или
  принимает решение. Делегирование **проговаривать вслух** одной строкой, не молча.
  Карта агентов — `CLAUDE.md`. Какой тир модели брать и что делать, когда агент не вернулся, — `.claude/docs/model-policy.md`
  (его ставит bootstrap). Что именно оффлоудить и как ставить задание — `.claude/docs/background-offload.md`.
- **Verify before ship.** Любое изменение закрывается проверкой, которую можно запустить
  (тест / сборка / линт). Не можешь проверить — не отправляй. См. `testing.md`.
- **Фича по макету → сверка с макетом перед «готово».** Соответствие замыслу, не пиксель в пиксель.
  Тестами это не закрывается: они проверяют поведение, а не то, что видит человек. Инструмент
  сверки и допуски — в языковом слое (`rules/lang/<lang>.md`), у CORE их быть не может.
- **Независимый ревью для нетривиального.** Правка многофайловая / меняет поведение / задевает
  CORE → перед «готово» ОДИН свежий ревью-агент. Self-review автора гейтом не считается: он
  делит слепые зоны автора. Мульти-агентная оркестрация — только по явному запросу владельца
  с озвученной ценой. Однострочный diff — без церемоний.
  Чеклист — `.claude/docs/REVIEW.md` (его ставит bootstrap), плюс языковая добавка из
  lang-pack, если она есть (`REVIEW-<lang>.md`).
  **Есть спека с AC-ID → сверка критериев идёт ПЕРВОЙ секцией ревью**, до остальных находок:
  вердикт по каждому ID (MET / PARTIALLY MET / UNMET / CANNOT ASSESS) со ссылкой на поведение,
  а не на наличие теста. Протокол и запреты — в `REVIEW.md`. Спеки нет → секция не запускается,
  критерии не выдумываются.
  **Фиксы по находкам — через чекпоинт:** однострочный чини сразу; пачка правок или правка
  поведения — показать находки и план, ждать подтверждения. Одобрение плана фичи НЕ
  распространяется на фиксы ревью — это новая развилка.
- **Перед релизом/тегом — ревью ЛЕСА, не диффа:** прогони смоук репы, сверь доку с реальностью,
  проверь публикуемость (приватное в git-ИСТОРИИ). Дифф-скоуп пропускает репо-wide баги и утечки.
- **«Тут так принято» бьёт любое правило: прецедент в коде сильнее строки в этом файле.**
  Агент, которому нужно решить, как что-то сделать, смотрит на соседний код — и повторяет то, что
  там уже стоит, а не то, что написано в правилах. Отсюда два следствия. Первое: получил не то,
  что просил — **ищи источник в репозитории**, а не переписывай формулировку правила; почти всегда
  оно «подсмотрело» это рядом. Второе: копипаста и разнобой перестают быть вопросом вкуса — они
  становятся входными данными для всей последующей генерации, и стоимость их накапливается.
  Поэтому чужой код читают не для вердикта «хороший / плохой», а чтобы следующая генерация вышла
  лучше. Одна правка в источнике дешевле десяти правок в результатах. Внешнее наблюдение
  (команды на потоке ~400k строк AI-кода), у нас не измерено — но объясняет случаи, когда правило
  есть, а поведение прежнее.
- **Build from failures.** MVP-набор, остальное по реальной боли. Не строить
  инфраструктуру под проблему, которой ещё нет.
- **Наблюдения не теряются.** Заметил нечто стоящее по ходу — `/note` (или прямой
  append в `.claude/PENDING-NOTES.md`). Разбор — в `/end-session`.
- **Закрываю единицу работы → онбординг + «как проверить» + comprehension-gate.** Задача
  не закрыта, пока владелец не подтвердил ПОНИМАНИЕ, а не только «тесты зелёные». Минимум:
  что делает фича, как проверить руками, где её границы. Как делить «понимаешь / на доверии» —
  `.claude/docs/completion.md`.
