# harness-template

Language-agnostic шаблон харнесса для **Claude Code**.

Харнесс — это обвязка вокруг агента: `CLAUDE.md` как точка входа, хуки на четырёх ярусах
проверки, skills вместо повторяющихся промптов, path-scoped правила и связь с долгосрочной
памятью. Ядро не зависит от стека: Vue, .NET, Go, PHP, python. Языковая специфика лежит
отдельным слоем (`rules/lang/` + `lang-packs/`).

Ярусы 1–3 (sensor, gate, pre-push) шаблон ставит сам. **Ярус 0 (pre-commit) не ставит:**
линтер и форматтер у каждого стека свои, их заводит проект. Раскладка ярусов —
в [docs/architecture.md](docs/architecture.md).

## Зачем

Модель недетерминирована. Она мыслит токенами и не знает специфики твоей кодовой базы,
поэтому без структуры агент застревает, галлюцинирует и тихо ломает логику.

Харнесс компенсирует четыре вещи:

- **Контекст** — не дать агенту попасть в «глупую зону».
- **Верификация** — не доверять выводу, а проверять хуками на exit-кодах.
- **Оркестрация** — длинные задачи разбиты на шаги с сохранением состояния.
- **Изоляция** — безопасное выполнение в песочницах.

Это supervised-харнесс: человек на цикле, не автономный loop-runner. Набор сознательно
MVP, дальше растёт от реальных отказов.

## Установка

### Новый проект — одной командой

```bash
mkdir -p myproj && cd myproj
bash /path/to/harness-template/scripts/bootstrap.sh myproj python
# lang: python | vue | react | go | php | dotnet | none   (--agents — доставить роли субагентов)
# extra_langs: доп. паки для монорепы — python на бэкенде, react на фронте
```

Скрипт делает `git init`, раскатывает харнесс, заполняет `.harness.conf` под выбранный язык
и включает Ярус 3 на `.git/hooks/pre-push`. Для `python` дополнительно ставит зависимости
через `uv`, создаёт `tests/test_smoke.py` и гоняет `pytest`. Другие языки этот шаг не получают:
тестовый раннер у каждого свой.

Папка обязана быть пустой. В непустой скрипт откажется работать, чтобы `git init` не уехал
в каталог с чужим проектом.

### Существующий проект — раскатать в сторонке и перенести

Bootstrap рассчитан на чистую папку. Поверх живого репозитория его не гонять, поэтому
разворачиваем во временной и переносим только части харнесса:

```bash
# 1. Раскатка в сторонке
T=$(mktemp -d) && (cd "$T" && bash /path/to/harness-template/scripts/bootstrap.sh myproj python)

# 2. Перенос в свой проект
cd /path/to/myproj
rsync -a "$T/.claude" "$T/scripts" ./
cp "$T/.harness.conf" ./
cp "$T/.copier-answers.yml" ./          # без него позже не сработает copier update
cp "$T/CLAUDE.md" ./CLAUDE.harness.md   # свой CLAUDE.md не перезатирать, слить руками
mkdir -p docs/specs && cp "$T/docs/specs/_template.md" docs/specs/ && cp "$T/docs/MOC.md" docs/

# 3. Ярус 3 на pre-push (логика в .claude/guards/pre-push.sh, приезжает с харнессом)
printf '#!/usr/bin/env sh\nsh "$(git rev-parse --show-toplevel)/.claude/guards/pre-push.sh"\n' \
  > .git/hooks/pre-push && chmod +x .git/hooks/pre-push

rm -rf "$T"
```

**Потом обязательно открой `.harness.conf`.** Он приехал с командами того языка, которым
раскатывали, и в твоём проекте их может не быть вовсе. Проверка на живом репозитории даёт
`GATE FAILED` именно на этом. Все параметры с комментариями лежат внутри самого файла.

Команды шарятся через `package.json`? Тогда вместо git-хука ставь husky:
`cp skeleton/.husky/pre-push .husky/pre-push && chmod +x .husky/pre-push`, а в `package.json`
добавь `"prepare": "husky || true"` (`|| true` чтобы CI не падал без husky).

Языковой пакет поверх ядра копируется руками: `cp -r skeleton/lang-packs/vue/skills/* .claude/skills/`.

> Версионируемый sync ядра — через [Copier](https://copier.readthedocs.io) (`copier update`).
> Установка и обратный канал описаны в [docs/architecture.md](docs/architecture.md).

## Проверить, что живо

**В проекте** с раскатанным харнессом:

```bash
bash scripts/verify-harness.sh
```

Восемь проверок: конфиг читается, guard блокирует readonly-зону и пропускает разрешённый путь,
sensor и gate на месте, защита gate от петли держит, `/note` исполняем. Коды выхода:
`0` всё живо · `1` что-то сломано · `3` запущено не в проекте, поэтому ничего не проверено.

**В самом шаблоне** гонять нужно другое — проверки каналов доставки, а не харнесса:

```bash
bash scripts/verify-bootstrap.sh     # канал bootstrap: раскатка, хуки, лог, сверка AC, Ярус 3
bash scripts/verify-copier.sh        # канал Copier: CORE доехал, личное и не-CORE не протекло
bash scripts/check-docs-reality.sh   # доки против кода: числа, ссылки, устаревшие утверждения
bash scripts/lint-core-purity.sh     # стек-специфика в CORE (порог — ноль)
bash scripts/lint-shell.sh           # синтаксис всех .sh: bash-файлы bash'ем, POSIX — dash'ем
```

Все пять сразу — `bash scripts/verify-all.sh` (~28s, без fail-fast).

## Что где лежит

| Путь | Что там | Кого касается |
|---|---|---|
| `skeleton/` | всё, что уезжает в проект. Меняешь тут → меняешь, что получит потребитель | автор шаблона |
| `skeleton/.claude/` | сам харнесс: `guards/` (хуки), `skills/` (команды), `rules/` (правила), `docs/` (шаблоны памяти) | и автор, и проект |
| `skeleton/scripts/` | CORE-скрипты, которые проект зовёт в рантайме (лог, сверка AC, покрытие, смоук) | проект |
| `skeleton/lang-packs/` | языковые пакеты поверх ядра. Копируются руками, автоматика их не возит | проект |
| `scripts/` | инструменты самого шаблона: раскатка, самопроверки, гейт чистоты CORE. В проект не уезжают | автор шаблона |
| `docs/` | архитектура, методология, ADR. Для людей, не для рантайма | все |
| `CLAUDE.md` + `.claude/` в корне | харнесс для работы над самим шаблоном (dogfood). Меняешь тут → меняешь, как работаешь ТУТ | автор шаблона |

Два слоя легко перепутать, и это главный источник ошибок в этой репе: `skeleton/.claude/`
уезжает потребителю, корневой `.claude/` остаётся здесь.

## Scope: что входит, что — концерн проекта

Границу стоит держать явной, иначе от шаблона ждут лишнего.

**В шаблоне:** guides и sensors (хуки), внешнее состояние, spec-driven флоу, гигиена контекста,
четыре яруса проверки, языковые слои.

**Не в шаблоне, добавляется в проекте по реальной боли:** MCP-коннекторы, loop-автоматизации и
worktree-параллелизм, мульти-агентная оркестрация, eval-слой на LLM-judge. Это не долг и не
пробел: набор зависит от стека и от того, где у проекта болит.

## Когда НЕ нужно

- Проект младше недели. Overhead не окупится.
- Нет тестов. Sensor без тестов бесполезен.
- Один разработчик без AI-агентов. Харнесс сделан для агентов, не для людей.
